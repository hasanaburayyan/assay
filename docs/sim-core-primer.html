r2ts engineering primer · Simulation core

The simulation doesn't know it's being watched.

An automation game is a simulation with a window bolted on. This primer shows how to build that simulation as its own program: plain data, a fixed clock, commands in, snapshots out. The renderer, whether Godot, Unity or a test harness, just watches. Every example uses a tiny factory with a custom-claw inserter, so the ideas map straight onto our game.

Chapter 1

Two programs, one direction

Split the game into two parts with a hard wall between them. The simulation owns the truth: where every item is, what every machine is doing, how much ore is left. The renderer owns everything the player sees and hears. Data flows one way. The renderer reads the simulation, and the simulation never reads, calls or imports the renderer.

The only way to change the simulation is to send it a command. Player clicks, drone AI and network messages all become commands. The simulation then advances in fixed steps called ticks.

The architecture

arrows = data flow
Simulation owns
  • Every entity's real position and status
  • Recipes, machine designs, ore stats
  • The tick counter and the seeded random generator
  • Rules: what can connect, what's blocked, what breaks
  • Nothing about pixels, frames or seconds
Renderer owns
  • Sprites, meshes, camera, zoom, UI panels
  • Smooth motion between ticks (interpolation)
  • Animations, particles, sound effects
  • Turning mouse clicks into commands
  • Anything cosmetic: skins, screen shake, tooltips

A quick test for any new code: "If we deleted Godot tomorrow, would this still need to exist?" If yes, it belongs in the simulation. If no, it belongs in the renderer.

Chapter 2

State is just data

The whole world should be a pile of plain structs: numbers, arrays and IDs. No sprite references, no engine nodes, no callbacks. If you can serialize it to a file and load it back, you have a save system, a replay starting point and a network snapshot almost for free.

Entities refer to each other by ID, not pointer. IDs survive saving, loading and sending over a network. Pointers don't.

sim/src/state.rsRust · C# looks nearly identical
// The entire world. No engine types anywhere in this crate.
pub struct World {
    pub tick: u64,
    pub rng: Rng,                    // seeded, and part of the state
    pub belts: Vec<Belt>,
    pub inserters: Vec<Inserter>,
    pub machines: Vec<Machine>,
    pub designs: Vec<InserterDesign>,  // player-made designs live here too
}

pub struct Inserter {
    pub id: EntityId,
    pub design: DesignId,             // which custom design it was built from
    pub from: EntityId,               // IDs, not pointers
    pub to: EntityId,
    pub phase: Phase,                  // Idle, Swinging, Returning
    pub timer: u16,                    // ticks left in this phase
    pub hand: ArrayVec<Item, 4>,
}

Your custom-inserter idea fits this cleanly. A design is data the player creates. The simulation derives an inserter's stats from its design, and the design also produces the recipe the factory must fulfil to build one.

pub struct InserterDesign {
    pub claws: u8,           // 1 claw vs 2 claws
    pub arm_length: u8,
    pub filter: bool,
}

impl InserterDesign {
    // Stats come from the parts, so design choices are real trade-offs.
    pub fn swing_ticks(&self) -> u16 { 10 + 3 * self.arm_length as u16 + 2 * self.claws as u16 }
    pub fn power_draw(&self)  -> u32 { 40 * self.claws as u32 + if self.filter { 25 } else { 0 } }
    pub fn recipe(&self) -> Recipe {  // what the factory must produce to build one
        Recipe::new()
            .input(Item::Claw, self.claws as u32)
            .input(Item::ArmSegment, self.arm_length as u32)
            .input_if(self.filter, Item::Sensor, 1)
    }
}
Chapter 3

Commands are the only way in

The renderer never changes state directly. When the player drags out a building, the UI creates a Command, stamps it with the tick it should apply on, and queues it. The simulation applies it at the start of that tick.

This one rule gives you four features. Save the command list and you have a replay. Send it to other players and you have multiplayer. Feed a scripted list into a test and you have automated tests. And your drones and AI planners use the exact same commands as the player, so there's only one code path to debug.

pub enum Command {
    PlaceMachine   { design: DesignId, at: TilePos, rotation: Dir },
    SetDesign      { inserter: EntityId, design: DesignId },
    QueueBlueprint { blueprint: BlueprintId, origin: TilePos },  // drones build it over time
    Deconstruct    { area: TileRect },
}

pub struct Input { pub tick: u64, pub player: PlayerId, pub cmd: Command }

Validate commands inside the simulation, not the UI. The UI can grey out a button, but the simulation decides whether "place machine here" is legal. That matters in multiplayer, where the UI on another machine might be out of date.

Chapter 4

The tick: one step of the world

A tick is one discrete step. Each tick runs the same systems in the same fixed order. The order is part of the rules. If inserters run before belts, an item can arrive and get grabbed in the same tick. Swap them and it takes an extra tick. Either is fine, as long as it never changes.

Apply commands→Mines→Belts→Inserters→Machines→Drones→Emit events→tick += 1 
pub fn step(world: &mut World, inputs: &[Input], events: &mut Vec<Event>) {
    for input in inputs { commands::apply(world, input); }

    mines::update(world);
    belts::update(world);
    inserters::update(world, events);
    machines::update(world, events);   // pushes Event::Crafted { machine, item }
    drones::update(world);

    world.tick += 1;
}

Notice what's missing: no delta_time. The simulation counts in ticks, not seconds. A machine doesn't take "0.5 seconds" to craft, it takes 30 ticks. That keeps the math exact and makes every run repeatable.

Events are the simulation's way of saying "something happened" without knowing who cares. The renderer turns Crafted into a sound and a puff of steam. The stats panel counts them. The simulation doesn't know either exists.

Chapter 5

Fixed ticks, smooth frames

Screens refresh at 60, 120 or 144 Hz, and frame times wobble. The simulation shouldn't care. The standard fix is the accumulator loop. Each frame, add the real elapsed time to a bucket. While the bucket holds at least one tick's worth, run a tick. Whatever is left over tells the renderer how far it is between the last tick and the next one.

Frames vs. ticks

ticks at 20/s · frames uneven

Each frame draws the world blended between the two most recent ticks, weighted by α (alpha). The player sees smooth motion even if the simulation only ticks 20 times a second. Some frames run zero ticks and some run two. That's expected.

const TICK: f64 = 1.0 / 60.0;   // one tick = 1/60 s of game time
let mut acc = 0.0;

loop {
    acc += frame_time().min(0.25);     // clamp so a stall can't trigger 1,000 catch-up ticks
    while acc >= TICK {
        prev = snapshot(&world);          // keep the old view for blending
        step(&mut world, queue.take(world.tick), &mut events);
        acc -= TICK;
    }
    let alpha = acc / TICK;              // 0.0 .. 1.0
    render(&prev, &snapshot(&world), alpha);
}

That clamp guards against the "spiral of death": a slow frame causes more catch-up ticks, which makes the next frame slower. Cap it, and if the factory truly can't keep up, the game slows down instead of freezing.

Chapter 7

Determinism: same inputs, same world

A simulation is deterministic if the same starting state plus the same commands always produce exactly the same result, down to the last bit. It sounds academic. It's what makes replays, lockstep multiplayer, bug reproduction and regression tests possible. Factorio's multiplayer relies on it: every player runs the full simulation and only commands go over the network.

Determinism is easy to keep from day one and very painful to add later. Six rules cover most of it:

1
All randomness comes from a seeded generator stored in the state.

Never call a global random function. The generator's internal state is saved, loaded and hashed like everything else. The demo's bug checkbox breaks exactly this rule.

2
Never read the clock inside the simulation.

No Instant::now(), no DateTime.Now, no frame delta. The tick counter is the only clock.

3
Iterate in a stable order.

Rust's HashMap iteration order is randomized per process by default. Use Vec, sorted IDs, or an ordered map for anything the rules loop over.

4
Be careful with floating point.

Basic float math repeats reliably on one build, but results can drift across platforms and compilers, especially with functions like sin and pow. Use integers or fixed-point for anything that affects game rules: positions on belts, recipe timers, ore quality.

5
Threads may only split independent work, and results merge in a fixed order.

Two planets can simulate on two threads. Two threads racing to take the same item is a desync.

6
Hash the state and check it.

Hash the world every N ticks. In tests, compare against a recorded replay. In multiplayer, compare between peers. When hashes differ, you know the exact tick things went wrong.

Chapter 8

Wiring it into Godot

The simulation is a normal library with its own tests. Godot loads it through GDExtension (for Rust, via the godot-rust bindings; for C#, as a regular project reference). One small bridge node owns the World, ticks it, and hands snapshots to the view nodes.

Repo layout
r2ts-game/
├─ sim/               # the game's rules. No Godot.
│  ├─ src/state.rs
│  ├─ src/step.rs
│  ├─ src/systems/    # belts, inserters, machines…
│  └─ tests/          # run with cargo test
├─ sim-bench/         # headless perf runs
├─ sim-godot/         # thin GDExtension wrapper
└─ godot/             # scenes, sprites, UI, audio
   └─ SimHost.gd
godot/SimHost.gdthe only bridge
extends Node

var sim := Sim.new()   # class exported by sim-godot
var queue := []

# Godot calls this at a fixed rate (60/s by default).
func _physics_process(_dt):
    sim.step(queue)
    queue.clear()

# Called every rendered frame.
func _process(_dt):
    var a := Engine.get_physics_interpolation_fraction()
    $FactoryView.draw_from(sim.prev(), sim.curr(), a)

func place_machine(design, tile):
    queue.append({"type": "place", "design": design, "at": tile})

Godot's _physics_process gives you a fixed-rate tick for free, and Engine.get_physics_interpolation_fraction() is the α from Chapter 5. Keep Godot's own physics engine out of the simulation: belts and inserters are your rules, not rigid bodies. For thousands of items, draw with MultiMeshInstance2D instead of one node per item.

Chapter 9

What the split buys you

This is the reason to do it. The test below builds a factory from a blueprint, runs a game-minute in a few milliseconds, and checks a design claim. No window, no engine, and it runs in CI on every commit.

#[test]
fn two_claw_inserter_beats_one_claw() {
    let one = throughput("tests/line.bp", InserterDesign { claws: 1, ..base() });
    let two = throughput("tests/line.bp", InserterDesign { claws: 2, ..base() });
    assert!(two > one);
    assert!(two < one * 2, "2 claws should help, not double: the assembler should bottleneck");
}

fn throughput(bp: &str, design: InserterDesign) -> u32 {
    let mut w = World::from_blueprint(bp, design, 42);  // 42 = seed
    run(&mut w, 60 * 60);          // one game-minute, headless
    w.stats.crafted(Item::Gear)
}

Balance tests

Assert that no design dominates. Run every claw, arm and filter combination overnight and flag any that's strictly better than the rest.

Performance budget

Benchmark a 100k-entity megabase in CI. If a change makes a tick slower than your budget (for example 8 ms), the build fails.

Bug reports as replays

Players attach a save plus the command log. You replay it tick-for-tick on your machine and step to the exact moment it broke.

Server and co-op later

The same library runs as a headless dedicated server, or in lockstep on every player's machine. No rewrite needed.

Chapter 10

Deeper topics

Where to go next, roughly in the order you'll need them. Each card says why it matters for the game we discussed: custom machines, procedural ores, multiple planets, and drone-built megaprojects.

Prototype

Data-oriented design

Store entities in tightly packed arrays grouped by type ("struct of arrays") so the CPU streams through them. Objects scattered in memory with virtual calls get slow fast.

For us: a factory game is millions of tiny updates per second. Layout decides whether a megabase runs at 60 ticks/s or 12.

Search: Mike Acton "Data-Oriented Design and C++" · ECS · bevy_ecs · flecs

Prototype

Sleeping entities

Most machines are waiting most of the time: output full, input empty. Put them to sleep and wake them only when something they depend on changes. Only active entities cost CPU.

For us: a big base might be 90% idle machines on any given tick.

Search: Factorio Friday Facts on active entities · event-driven wakeups

Vertical slice

Belt and transport optimization

Don't move every item every tick. Treat a straight run of belt as one segment and store the gaps between items. Moving the whole segment then means updating one number.

For us: belts usually hold the most entities in the game.

Search: Factorio Friday Facts belt optimization · transport lines

Vertical slice

Procedural generation from seeds

Make ore deposits a pure function of (world_seed, planet_id, chunk_x, chunk_y). Then you never store the untouched world, only the chunks players changed.

For us: "ore gets better the deeper you go" becomes a formula of distance plus seeded noise, identical on every machine.

Search: coherent noise · simplex/OpenSimplex · hash-based noise · chunked worlds

Vertical slice

Save files and versioning

Serialize the world to a compact binary format with a version number. Write migrations so old saves load in new builds. Early access players will expect saves to survive updates.

For us: player-made machine designs are save data too. Changing part stats needs a migration story.

Search: serde + bincode/postcard · schema evolution · save migrations

Vertical slice

Fixed-point math

Represent fractional values as scaled integers (for example 1 unit = 1/256 tile). You get exact, platform-independent results and no float drift.

For us: belt positions, crafting progress and ore purity percentages.

Search: fixed-point arithmetic · the fixed crate (Rust)

Early access

Simulation level of detail

Distant, unobserved areas don't need item-by-item simulation. Once a sub-factory is stable, model it as rates ("12 gears per minute, consuming 24 ore") and step it cheaply. Switch back to full detail when a player arrives or something changes.

For us: essential for multiple planets. You can't fully tick ten planets at 60/s.

Search: simulation LOD · statistical simulation · rate-based production

Early access

Drone job planning

A blueprint becomes a queue of jobs (fetch item, fly, place). Drones claim jobs, planners order them by dependency, and pathfinding runs per chunk. Keep all of it deterministic: same jobs, same drones, same assignments.

For us: this is your "macro" layer. Its rules live in the simulation; the plan UI lives in the renderer.

Search: job systems · flow fields · hierarchical pathfinding (HPA*) · task allocation

Early access

Parallel simulation

Split work into regions that don't touch (planets, or chunks with buffers between them). Run them on separate threads, then merge the results in a fixed order to stay deterministic.

For us: planets are a natural boundary. Interplanetary shipments can move between them at fixed sync points.

Search: deterministic parallelism · rayon · double-buffered state

If we do co-op

Lockstep multiplayer

Every player runs the full simulation. Only commands go over the network, scheduled a few ticks ahead to hide latency. Bandwidth stays tiny even with a huge factory. Joining mid-game means transferring a save.

For us: the reason determinism has to be there from day one.

Search: "1500 Archers on a 28.8" · deterministic lockstep · Factorio multiplayer

If we do co-op

Desync hunting

When two peers' hashes disagree, dump both states, diff them, and bisect ticks to find the first divergence. Build the tooling early. It's miserable to build during a crisis.

For us: a debug overlay that shows the hash per subsystem (belts, machines, drones) points straight at the culprit.

Search: desync debugging · per-system state hashing

Post-launch

Modding boundary

Expose a scripting API (for example Lua) that can add recipes, parts and entities, and issue commands, but runs inside the tick in a deterministic sandbox.

For us: custom parts are a natural mod surface. Factorio's Lua API is the reference design.

Search: mlua · Factorio modding API · sandboxed scripting
